# Production deployment (free tier)

The Android app talks to a hosted API, so phones work without the development PC or Docker running.

| Part | Service (free plan) | Why |
|---|---|---|
| API (FastAPI, Docker) | **Render** web service, Singapore, `render.yaml` | Public HTTPS, Docker, no card needed for free web services |
| Database | **Neon** Postgres 18, AWS Singapore (`ap-southeast-1`) | Permanent free plan (Render's free Postgres is deleted after 30 days) |
| AI assistant + crop-photo check | **Ollama Cloud** (`https://ollama.com`, same API as local Ollama) | No code path change; no PC needed |
| Sign-in | Phone + password, admin approval of new testers | No SMS service or phone needed (see "Sign-in and tester access") |
| Weather | Open-Meteo (no key) | unchanged |

Limits checked on 2026-10-15:

* **Render free**: 512 MB RAM, 0.1 CPU; sleeps after **15 min** without requests and takes **about 1 min** to wake;
  750 instance-hours/month per workspace (enough for one always-reachable service). The app waits up to 90 s
  (`API_RECEIVE_TIMEOUT_SECONDS`), so the first request after a quiet period is slow, not failed. Measured memory use:
  about 125 MiB.
* **Neon free**: 0.5–1 GB storage per project (current data: 11 MB), 100 compute-hours/month, compute sleeps after
  5 min idle (first query then takes about 0.5 s), **6-hour** point-in-time restore window. Not a backup: run
  `scripts/backup-prod-db.ps1` yourself (below).
* **Ollama Cloud free**: a starter usage allowance that resets monthly, 1 request at a time (others queue). When the
  allowance runs out, or a model is not available on the free plan, the assistant falls back to its non-AI answers
  and the photo check falls back to colour measurements; both say so. Nothing else is affected.

## One-time setup (needs your accounts)

1. **Neon**: sign up at <https://neon.com> (no card), create project `harvestique`, Postgres 18 (the current default), region
   *AWS Asia Pacific (Singapore)*. In *Connect*, turn **off** "Connection pooling" and copy the connection string
   (`postgresql://...neon.tech/neondb?sslmode=require`).
2. **Copy the existing data** into the new empty database **before the first Render deploy** (the server creates its
   tables at start-up, and the script refuses a database that already has tables):
   ```powershell
   $env:TARGET_DATABASE_URL = "<Neon connection string>"
   powershell -ExecutionPolicy Bypass -File scripts\restore-to-empty-db.ps1 -Dump ..\harvestique-backups\<latest local dump>
   Remove-Item Env:TARGET_DATABASE_URL
   ```
   Take a fresh local dump first if the local data changed (`docker exec harvestique-db-1 pg_dump -U harvestique -d
   harvestique -Fc --no-owner --no-acl > ..\harvestique-backups\harvestique_local_<date>.dump`).
3. **Ollama Cloud**: sign in at <https://ollama.com>, create a key at <https://ollama.com/settings/keys>.
4. **Render**: sign up at <https://render.com> with GitHub and allow access to the `harvestique` repository (it is
   private: choose it under "Only select repositories"). *New > Blueprint*, pick the repository and branch
   `deploy/free-tier-production` (or `main` once merged); Render reads `render.yaml` and asks for only two values:
   `DATABASE_URL` and `OLLAMA_API_KEY`. `JWT_SECRET_KEY` is generated by Render. No SMS settings exist any more.
   If the name `harvestique-api` is taken, Render adds a suffix: put the real URL in
   `frontend/config/production.json`. The first start applies the pending migrations (0016 tester access, 0017
   password resets; both only add columns), so run the backup script first if the database already holds data.
5. Check: `https://harvestique-api.onrender.com/api/v1/health/ready` returns `"status":"ready"`, then run
   `scripts/verify-production.ps1` (HTTPS, health, CORS, auth refusals, no SMS-code endpoints).
6. **Admin account** (for approving testers), on the hosted database **after** the first deploy (it needs the new
   columns); you type the password, it is never shown:
   ```powershell
   $env:PROD_DATABASE_URL = "<Neon connection string>"
   powershell -ExecutionPolicy Bypass -File scripts\create-prod-admin.ps1 -Phone +91XXXXXXXXXX -Name "Your Name"
   Remove-Item Env:PROD_DATABASE_URL
   ```

## Sign-in and tester access

Sign-in is **mobile number + password**. No SMS is sent at any point, so no phone, SIM or SMS service is needed.
Production sets `NEW_ACCOUNT_ACCESS=pending` (and refuses to start with anything else): a person who installs the APK
can create an account but sees "waiting for approval" and gets no session until an admin approves them. The phone
number is **not** verified by the app any more, so the approval is the identity check: before approving, make sure
you know the person and that the number is theirs (for example, call it). Sign in with the admin account and open
**Testers**:

* **Approve**: the person can sign in.
* **Suspend**: blocked on their next request; their sessions are kept, so approving again lets them continue.
* **Revoke access**: blocked and signed out on every phone; approving again needs a fresh sign-in.
* **Reset password** (forgotten password): first check that the request really comes from that person. The app shows
  a one-time **temporary password** (only once; it is stored only as a hash). Give it to them privately. They are
  signed out everywhere, and at their next sign-in they must choose a new password before they get a session.

Anyone signed in can change their password from the account menu (**Change password**); other devices are signed out.
An admin who forgets their own password is reset by an operator on the hosted database (password typed hidden):

```powershell
$env:PROD_DATABASE_URL = "<Neon connection string>"
powershell -ExecutionPolicy Bypass -File scripts\set-prod-password.ps1 -Phone +91XXXXXXXXXX
Remove-Item Env:PROD_DATABASE_URL
```

Protection without a second factor: passwords are stored as Argon2id hashes; new passwords need 8+ characters with
letters and digits and may not be a well-known password; each number is locked for 15 minutes after 5 wrong
passwords and for up to a day after 20 in a day (a correct password or an admin reset clears it); sign-up is limited
to 30 new accounts an hour across the server; unknown numbers and wrong passwords get the same answer; and signing up
with a number that already has an account gets the same "waiting for approval" answer without changing anything.
Existing sessions stay valid (they were issued after SMS verification). The SMS-era `otp_challenges` table is kept,
unused, so no data was dropped.

The server checks access on every request, token refresh and sign-in, so a decision applies within seconds, not at
token expiry. Admin accounts cannot be suspended through the API (no lock-out). Accounts copied from the local
database are `approved`. The same is available as `GET /admin/users?access=pending` and
`POST /admin/users/{id}/access` (`{"status": "approved" | "suspended" | "revoked"}`); a password reset is
`POST /admin/users/{id}/password-reset`, and the person then calls `POST /auth/password/change`.

Auto-deploy is **off** (several sessions push to `main`). Deploy on purpose: Render dashboard > *Manual Deploy*.
Migrations run at container start (`alembic upgrade head`); the existing ones only add tables/columns or swap check
constraints. **Before deploying a new migration, run the backup script.**

## Backups

```powershell
$env:PROD_DATABASE_URL = "<Neon connection string>"
powershell -ExecutionPolicy Bypass -File scripts\backup-prod-db.ps1   # writes ..\harvestique-backups\harvestique_prod_<time>.dump
Remove-Item Env:PROD_DATABASE_URL
```

Run it weekly and before every deployment with a migration. Restore only into a new, empty Neon branch or project
with `scripts/restore-to-empty-db.ps1`, check it, then point `DATABASE_URL` at it. Never restore over the live
database.

## Signing key (keep it safe)

Release APKs are signed with `frontend/android/app/upload-keystore.jks`, described by `frontend/android/key.properties`.
Both are git-ignored. A copy is in `..\harvestique-backups\android-signing\`; also keep one off this PC (e.g. a
private cloud drive). Without it, no future APK can update the installed app: every user would have to uninstall it
first.

Phones that have an older **debug** build installed must uninstall it once before installing the release APK
(different signature). Their data is on the server, so nothing is lost; they sign in again.

## Rebuilding the shareable APK

```powershell
powershell -ExecutionPolicy Bypass -File scripts\build-release-apk.ps1
```

The script refuses a localhost / LAN / non-HTTPS server address, checks the hosted server is ready, runs the Flutter
tests and builds `frontend\build\app\outputs\flutter-apk\app-release.apk` (prints size and SHA-256). Raise
`version` in `frontend/pubspec.yaml` (e.g. `0.6.1+7`) before each new release so phones accept it as an update.
Share the APK file directly (WhatsApp, Drive); receivers must allow "Install unknown apps". Android 7.0+.

## Limitations

* The first request after 15 idle minutes waits about a minute (free Render sleeps).
* Sign-in has no second factor: a guessed or shared password gives access to that account. The lockouts above slow
  guessing, but a person who reuses a password from another site is exposed. Ask testers to use a password unique to
  Harvestique.
* The lockout is per phone number, so anyone who knows a tester's number can lock them out for up to a day by typing
  wrong passwords; an admin password reset unlocks them at once.
* AI answers and the photo check use `gemma4:31b` on Ollama Cloud. That model has **not** been evaluated on the
  project's crop-photo sets (the published numbers are for local `gemma3:4b`) nor for Kannada answers; Kannada general
  answers stay off (`ASSISTANT_LLM_GENERAL_ANSWERS_KANNADA=false`). Results remain advisory.
* Without `OLLAMA_API_KEY`, `/health/ready` shows `llm:disabled` and the AI features use their non-AI paths. With a
  key it shows `llm:ollama ok` when the model is listed, even if the key is wrong or the allowance is used up; real
  failures then fall back as described.
* Crop photos are analysed in memory and only the results are stored in the database, so Render's temporary disk
  loses nothing on restart.
* Live mandi prices stay off unless you add a free `DATA_GOV_IN_API_KEY` and set `MARKET_PRICE_PROVIDER=data_gov_in`.
